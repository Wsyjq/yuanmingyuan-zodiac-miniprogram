# 剧本内容包与快速调整指南

## 设计目标

只调整剧情、题干、史料、道具说明、既有选项和段落衔接时，修改内容包；页面外观、存档、音频生命周期和玩法组件复用。不承诺任意新玩法零代码，也不把 Word 自动识别当作已审校内容。

## 一处维护的内容

目录：`plate21/module/content/`。

| 文件 | 负责内容 |
|---|---|
| story.js | 版本、43 个当前节点、页标题、剧情段落、独立互动文案、史料词条、所需道具、音频 ID、next/skipTo、演出标记 |
| history.js | 史料标题、完整 layers、图片和图注；年份由正文自动提取，不手填重复副本 |
| props.js | 道具名称、操作步骤、何时返回屏幕 |
| tasks.js | 当前任务、操作摘要、提示及失败反馈 |
| puzzles.js | 现有单选题选项及答案 ID、拼字允许答案 |

旧 `flow/pages.js` 是编译入口，`script-content.js`、`glossary.js`、`props.js`、`utils/sl-cards.js` 是兼容适配层，不再各自存一份正文。数据 → 编译与校验 → 流程引擎 → 现有 WXML 模板。正文、互动和史料持续分开，未改变整体视觉。

## 改一句话、移动一段、调整史料

1. 在 story.js 查对应稳定 id（如 XS1），改 lines 中的文字。每项为一个自然段。
2. 玩法题干/说明放在 interaction.lines，不能混回剧情 lines；互动标题为 interaction.title。
3. 揭晓沿用独立节点 revealOf 或原有 interaction.requires，不能把答案直接挪到答题前的正文。
4. terms 中的 key 对应 history.js 的卡号；label 是正文中高亮的词，aliases 可兼容同义写法。
5. props 是道具目录的键，例如 ["bulletin"]；详细步骤只改 props.js。
6. 如旧旁白与修改后的文字不一致，暂将该页 narrId 置空，保留纯文本；补录听审后按音频清单接回。不要继续播放过期答案。
7. 更新 story.revision 为本轮可辨认版本。它是内容修订标记，不自动清空存档，也不是宿主版号。

## 插入普通剧情页示例

在 P1 后插入阅读页时，把 P1.next 从 P2 改为 P1_note，并将以下节点放在 nodes 数组中 P1 后面：

```js
{
  "id": "P1_note",
  "kind": "read",
  "title": "补充档案",
  "lines": ["这里填写新增剧情。"],
  "terms": [{ "key": "sl01", "label": "铜版图" }],
  "props": [],
  "narrId": "",
  "next": "P2"
}
```

只修改配置即可进入、阅读和继续；不新增微信路由、不改 walk 页面、不另造存档。节点数组同时决定“返回”的阅读顺序，必须与 next 的顺序一致。新页要显式决定是否允许 skipTo，不默认沿用旧页跳转。

纯剧情段落删减可直接编辑 lines。移动已有页面时保持 id，只调整数组顺序和 next/skipTo；需核对站点结束、谜题揭晓和跳过出口。不要为了排版好看重新给整份剧本编号。

## 哪些变化仍需要开发

- 新的交互机制（如一种未实现的拼图）：增加一个玩法处理器/组件，再由内容节点引用；复用现有 session、史料、道具、报告能力。
- 新增相同玩法但独立判题的第二个任务：须注册新的玩法实例 ID；不可复制旧 playId，否则会共享完成状态。
- 中心亭照片、喷水动画、终局作品和接力等特殊功能节点，目前保留稳定能力代码。改变这些节点的职能需修改对应能力，不宣称它们已变成任意 JSON 演出系统。
- 大范围删除/重命名节点、修改站点结构或改动完成条件：先制定旧存档映射，不自动认定玩家完成新增任务，也不重写历史完成日期。

## 兼容旧记录

本次不改存储命名空间、不改已有节点/玩法 ID、不修改旧存档。只改文字时，玩家原进度继续使用，页面展示当前文案。已走过插入点的玩家不会被强制倒退补读新页；若产品需要补读，另行设计迁移。已完成作品的日期及本人记录不变，但历史剧情不按版本单独封存，回看使用当前内容包。

`tools/story-compatibility.json` 记录已发布到本地版本的节点 ID、类型和玩法。检查器会阻止直接删除、改类型或换玩法。若确需破坏性变化，应写迁移与回归测试后再有意更新兼容清单，不能删清单绕过报错。

## 每次接收新 Word 的流程

1. 比较新旧稿，列出增删改段落、玩法及史料变化；遵守用户明确的【】规则，不导入全局规划。
2. 建立新段落 → 稳定节点/interaction/史料卡的对应，保留来源段号；不得只更新一份孤立文本。
3. 编辑 content 文件；更新 Word 覆盖夹具 `test/fixtures/v3-script-coverage.json`，与新稿逐段人工核对，不直接批量接受测试结果。
4. 执行 `npm run check:story`；检查流程链接、循环/不可达页、重复玩法、史料、道具、答案和图片。音频映射提醒不代表已通过听审。
5. 执行 `npm test`；实测本轮改动的页面、前后转场和恢复点。
6. 分阶段 Git 提交，并保留变更前的版本。新剧本没有审核过的内容不会自动进入正式发布。

校验器能发现结构错误，不能替代历史事实审校、实体道具试玩、真机布局与录音听审。

## 剧情与玩法独立屏幕

`lines` 只承载剧情，`interaction.lines` 承载玩法说明与揭晓；两者现在分页显示，不会堆叠。默认顺序为剧情 → 玩法；`interaction.position: 'before'` 为互动解读 → 剧情。已有黄花阵翻面按操作 → 揭晓 → 剧情显示，中心亭为现场记录 → 剧情。没有 interaction 的节点仍是普通阅读页。后续仅调整两类正文即可自动延续分页。

分页投影位于 `flow/screen-parts.js`，以 `uiByPage[pageId].screenPart` 保存当前屏。剧情节点 ID、判题 ID 和主线链接保持稳定，不新增独立存储或无限叠加微信页面栈；玩家看到的是互斥的完整屏幕。返回先返回当前节点的前一屏，答题草稿保留。阅读前言不会标记任务完成；真实玩法通过后才能进入其后置剧情；跳过仍走原先 skipTo 与解锁规则。老存档缺少 screenPart 时按内容顺序显示，已翻面的存档从揭晓屏恢复。

## 彩蛋按语义段落展示

LT1—LT8 的 `dialogueGroups` 按顺序描述每段合并多少条原始 `lines`，例如 `[2, 2, 2]` 把六条文本合成三段。必须为正整数且总数等于 lines 长度，check:story 会检查；修改剧情后可直接调整这个数组，无需改组件。动态插入的保存/投稿状态文字独立显示，不吞掉原文。

letter-scene 不再按句号或 85 字截断；接收已经分组的段落，保留逐字显示、补全整段、下一段与回顾。长段落使用可滚动阅读区。新游标保存 `letterCursorVersion: 2`，旧句级游标转换到包含它的段落，避免更新后跳过整段。
