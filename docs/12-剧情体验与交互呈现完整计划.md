# 剧情体验与交互呈现完整计划

## 1. 文档定位

本文用于指导 `归途 · 十二兽首寻迹` 从“八个玩法可运行的功能 Demo”升级为“剧情、现场、玩法、视觉和反馈连续的完整体验”。

本文是后续讨论和开发的共同基线，不代表所有剧情文字、史实表述、素材和视觉细节已经定稿。

当前剧情母本为仓库外部资料《残垣无声_终稿》，因独立仓库边界和内容授权要求不随代码提交。

虽然文件名包含“终稿”，当前仍按最新剧情初稿处理。原文保留，不直接复制为主流程界面文案。

当前就绪范围：本文可用于指导第 23 节阶段 A 的内容拆解、史实核验和现场路线工作；当前工作矩阵见 [13-五章八互动阶段 A 详细矩阵](13-五章八互动阶段A详细矩阵.md)。在阶段 A 与 A2 通过条件全部满足前，不得据此直接替换现有八站路由、迁移用户记录、实现 beat 引擎或进入正式素材制作。

逐屏页面、转场、动效和素材制作规格见 [14-五章逐屏体验分镜与页面、动效、素材矩阵](14-五章逐屏体验分镜与页面动效素材矩阵.md)。该分镜以五地点顺序和知识目标为稳定骨架，剧情人物与具体玩法为可替换槽位。

本文重点解决：

1. 五个剧情章节如何承载现有互动玩法。
2. 玩家如何从一个地点自然进入下一个地点。
3. 剧情文字如何分层，避免主流程被长文阻塞。
4. 玩法如何从现场和道具中自然出现，而不是像独立小游戏合集。
5. 通关后如何通过环境变化、物件和情绪反馈完成过渡。
6. 图片、纹理、音频和动效如何服务叙事。
7. 剧情继续迭代时，如何避免重复修改页面和玩法代码。
8. 史实、剧情化改编和待现场核实内容如何区分。

本文暂不直接实施：

- 最终短文案定稿。
- 正式配音录制。
- 正式图片和音频批量制作。
- 宿主小程序接口接入。
- GPS 强制到点解锁。
- AR、VR、NFC 等后续增强能力。

## 2. 当前状态

### 2.1 已完成

- 微信原生小程序基础壳。
- 首页、地图、关卡、终局、记录和记录详情页。
- 八类互动玩法的基础实现。
- 本地进度、继续游玩、重新开始和历史记录。
- Mock 线路、用户和 Service 适配层。
- 静态、模拟器全流程和布局自动验证。
- 测试 AppID 下的真机预览链路。

### 2.2 当前体验形态

当前关卡页的流程基本是：

```text
地点标题
→ 剧情简介
→ 任务文字
→ 玩法组件
→ 成功 Toast
→ 约 450ms 后跳到下一关
```

当前主要问题：

- 八个玩法之间缺少统一的叙事线索和持续物件。
- 到达地点、观察现场、接受任务、完成任务和离开地点没有分层。
- 剧情简介和操作任务一次性出现，阅读负担较重。
- 通关后自动跳转过快，没有留下反馈和理解空间。
- 页面主要依赖相似的圆角卡片，章节个性不足。
- 十二枚印记长期占据顶部空间，容易强化“收集游戏”而削弱现场感。
- 现有素材主要位于 H5 参考产物中，尚未形成小程序正式素材体系。

### 2.3 新剧情与当前路线的差异

当前小程序路线为八个站点：

```text
大水法
→ 仙人呈露台
→ 途中信封
→ 海晏堂
→ 方外观
→ 盛时全景模型展
→ 黄花阵
→ 正觉寺
```

最新剧情母本采用五个主要地点：

```text
黄花阵
→ 海晏堂
→ 大水法
→ 远瀛观
→ 雨果雕像
```

因此不能只把新文字替换到旧路线里。需要重新定义剧情章节、互动节点和过渡关系，同时尽量保留已实现的玩法逻辑。

### 2.4 实现状态边界

本文描述的是目标架构，不是当前已实现行为。当前代码仍然：

- 以 `route.stages` 和 `p1` 至 `p8` 驱动八站流程。
- 允许页面参数和地图直接进入指定 stage。
- 只在整关完成时保存进度，没有 beat、interaction snapshot 或 journey。
- 使用全局 skip 发放 mark，并在完成后约 450ms 自动跳转。
- 在终局玩法完成后立即结束 session。
- 使用旧记录结构、旧模拟器脚本和旧布局脚本。

在第 22.7 节切换条件满足前，上述代码和自动化只能视为 legacy Demo。不能因为本文已经定义五章模型，就宣称五章体验、迁移或终章恢复已经完成。

## 4. 体验设计原则

### 4.1 现场先于说明

进入地点时先让用户看到现场图、环境和观察目标，再展示历史信息和玩法说明。

不采用：

```text
进入页面
→ 先阅读大段历史介绍
→ 再点击开始游戏
```

采用：

```text
到达现场
→ 看见一个具体对象
→ 得到一句观察提示
→ 从对象中进入玩法
```

### 4.2 行动先于解释

每次只告诉用户当前要做什么，不一次性解释完整背景。

历史信息在玩家完成观察或互动后出现，形成“先发现、后理解”。

### 4.3 主流程短，深读可选

主流程保证不愿阅读长文的游客也能完成体验。

愿意深入的用户可以在铜板工具包中打开林知远手记、历史档案和来源说明。

### 4.4 动效表达因果

动画必须回答“玩家刚才的动作改变了什么”。

例如：

- 迷宫接通后，灯火沿路径点亮。
- 时辰匹配后，水线从兽首流向水池。
- 拼图复原后，残垣切换为盛时景观。
- 时间线完成后，回归印记按年份落位。

不使用与内容无关的彩带、烟花、弹跳和大面积粒子。

### 4.5 用户主动推进

故事阅读、通关反馈和章节转场均由用户主动点击继续。

禁止在用户刚完成玩法后，使用短延迟自动跳到下一地点。

### 4.6 每章只有一个视觉记忆点

每章可以有多个轻微反馈，但只保留一个重点动效，避免持续高刺激和审美疲劳。

### 4.7 不制造虚假的完整结局

当前内容目标以经过审核且带有效日期的公开状态集为准。候选状态为：

```text
七尊完整回归
一尊仍在追索
四尊下落不明
```

上线前若核验结果仍为上述集合，四个空缺就是核心表达，不能被成功动画填满。若任何兽首公开状态发生变化，必须先更新来源、状态集、文案、时间线和终局，再发布新的 `contentVersion`；产品不能为了保留固定结语而覆盖新事实。

## 5. 总体信息架构

### 5.1 一级页面

| 页面 | 作用 |
|---|---|
| 序章首页 | 建立主题、打开数字路线包、开始路线 |
| 章节体验页 | 承载到达、观察、手记、玩法、发现和离开 |
| 地图转场页 | 显示当前地点、下一地点和步行方向 |
| 铜板工具包 | 保存信封、铜板、兽首状态、手记和档案 |
| 终章页 | 回归时间线、十二格终局和留言 |
| 游玩记录 | 保存完成状态、已解锁手记和最终留言 |

### 5.2 常驻界面

体验过程中只长期显示：

```text
章节进度 2/5
铜板工具包入口
地图入口
```

不长期展示完整十二兽首印记条。

点击铜板工具包后再展开：

- 陈敬民序章路线说明和五封地点数字信件的开启状态。
- 数字龙纹铜板。
- 已核验的兽首状态。
- 与陈敬民路线说明和地点信分开的林知远数字手记。
- 历史档案。
- 剧情化改编说明和来源。

第一版中的信封、铜板、拓印和印记均为数字叙事道具，不暗示园区现场真的藏有物件，也不引导游客触摸、移动或放置任何东西到遗址本体。若未来增加实体物料，必须另行定义发放、回收、点位授权和安全方案，不能沿用数字道具文案直接上线。

### 6.2 保留与调整原则

- 只保留经测试确认正确的纯玩法算法和判定逻辑。
- 新互动使用第 6.1 节稳定 ID；旧 `p1` 至 `p8` 只用于迁移来源映射，不承诺旧页面状态可直接恢复。
- 调整玩法出现顺序、视觉外壳、说明文字和完成反馈。
- `clock-match-game` 与 `sandtable-order-game` 的能力合并，不重复让用户完成两套十二项操作。
- `maze-path-game` 的迷宫和时间线拆到不同章节。
- 玩法从八个独立关卡变为八个互动节点，外部不再强调 p1 至 p8 编号。

### 6.3 完成、辅助完成与可选内容

当前 `skipRule.givesMark = true` 会把所有跳过都视为正常完成，不适用于新体验。新版本改为每个互动独立声明 `completionPolicy`，并遵守以下规则：

| 内容类型 | 正常完成 | 辅助方式 | 保存状态 | 是否发放后续必需内容 |
|---|---|---|---|---|
| 核心互动 | 玩家完成判定 | 分级提示后可“查看解法并继续” | 自行操作完成为 `completed`；系统展示答案为 `assisted` | 是，并记录提示级别 |
| 短转场互动 | 玩家完成短任务 | 可切换简化操作或直接查看结果 | 简化控件仍自行完成为 `completed`；直接展示结果为 `assisted` | 是 |
| 现场观察 | 玩家确认找到对象 | 无法到达时使用已审核现场图完成同一观察 | 自行确认均为 `completed`，另记 `accommodations[]`；系统直接指出答案为 `assisted` | 是 |
| 陈敬民信件 | 阅读主流程短句 | 无需读完整档案 | `completed` | 是 |
| 林知远手记 | 自愿打开 | 稍后阅读或始终不读 | `unread` 或 `read` | 不影响主线 |
| 结果动画 | 完整播放 | 允许减少动态或立即显示终态 | `completed`，另记 `presentationMode` | 是 |

必经互动不提供含义模糊的“跳过本关”。用户选择“查看解法并继续”时，系统展示结果和必要事实，发放保证后续可运行的故事物件，但在本次记录中标为 `assisted`。不设置隐藏惩罚，也不因运动、视觉、听觉或现场条件限制阻断路线。

`hint-1`、`hint-2` 记录到 `hintsUsed[]`，玩家随后自行完成仍记为 `completed`。减少动态、放大控件、替代输入和无障碍路线分别记入 `preferences`、`accommodations[]` 或 arrival receipt，不自动降为 `assisted`。每个互动必须在阶段 A 表中明确正常答案、提示层级、展示解法、替代操作和持久化结果，不能把这些决定留给组件自行推断。

构建校验只比较时间线、grant、终局和结语是否与获批状态集一致，不把“七、一、四”永久写死。若对象尚未获批或超过内容负责人定义的复核期限，生产构建失败。

`hugo.return-timeline` 和 `hugo.return-timeline.result` 获得唯一的 `statusReadCapability: 'pinned-status-set.preview'`，允许在解题和结果中读取 session 已固定但尚未发放的状态集。preview 只服务这两个 beat，不写 `zodiacStates`、不解锁工具包/档案，也不能被其他信件、手记或页面复用；持久发放仍只发生在 `hugo.status-set.grant`。

## 7. 有序节拍与行程状态

### 7.1 为什么不使用单次七阶段

`arrival → observe → note → playing → success → artifact → departure` 可以作为叙事词汇，但不能作为每章只运行一次的固定状态机。黄花阵包含迷宫、结果、铜板、信封拼字和地图转场；雨果雕像也连续包含时间线、结果、终局板和结语。同一章会重复出现互动、结果和物件节拍。

新版本使用“稳定 beat 列表 + 当前游标”：

```text
chapter.beats = [beatA, beatB, beatC, ...]
session.currentBeatId = beatC
```

`arrival`、`observe`、`letter`、`interaction`、`result`、`grant`、`departure` 和 `finale` 是 beat 类型，不是只能出现一次的全局 phase。章节间的可玩转场放在独立 `transition.beats` 中，与前后章节都不混为一个站点。

### 7.3 Beat 状态与推进规则

主线 beat 使用：

```text
locked
→ available
→ active
→ completed | assisted
```

规则：

- `currentBeatId` 永远指向当前可执行的主线 beat。
- 页面首次实际展示当前 beat 时调用幂等 `activateBeat`，第一次写入 `startedAt`；仅 `arrival` 类型同时执行第 7.6 节规定的 receipt 核对与 journey 归档，不允许其他隐式副作用。
- 互动 beat 只保存标准化结果，不直接发放物件或兽首状态。
- 只有 `type: 'grant'` 的专用 beat 可以修改 `inventory`、`zodiacStates` 和手记解锁状态。
- grant beat 分两次明确操作：`applyGrant` 写入全局 `grantLedger`、应用效果和 effect receipt，但不移动游标；`acknowledgeGrant` 确认物件卡后才完成 beat 并移动游标。同一个 `grantId` 在一个 session 中只能应用一次。
- 每个 grant 明确效果类型：`inventory.insert`、`note.unlock` 或 `zodiacStatusSet.attach`。未知效果、重复 insert、与 session 内容版本不一致的状态集都直接报错，不使用隐式 merge 或“校准”语义。
- `assisted` 与 `completed` 都可以推进主线，但记录页必须区分。
- 非阻塞手记单独保存 `locked`、`unread`、`read`，不伪装成主线 beat 已完成。
- 动画被跳过只影响呈现，不改变互动完成状态。
- 旧 `phase` 可以由当前 beat 的 `type` 派生，不再作为独立真实状态保存。

互动过程使用单独快照。只保存可稳定恢复的离散状态，例如拼图顺序、圆盘已锁定项、证据完成项和提示级别；雨滴位置、动画帧和临时触摸坐标不保存，恢复时回到该互动的安全检查点。`completeInteraction` 必须先把标准化结果和下一 beat 游标持久化；确认 grant 所需输入已经复制到标准化结果后，才能在后续独立操作中清理快照。grant 不得读取已完成玩法的私有快照。

### 7.4 Beat 类型完成契约

| Beat 类型 | 激活方式 | 完成动作 | 写入结果 |
|---|---|---|---|
| `content` | 展示一个主流程内容单元 | 点击明确的“继续” | 内容单元 ID、确认时间 |
| `action` | 展示单一流程动作 | 点击动作按钮 | 动作 ID、确认时间 |
| `arrival` | 到达确认后展示地点主视觉 | 点击“开始观察” | `arrivalReceiptId`、主视觉确认时间 |
| `observe` | 展示已审核观察目标 | 点击“我看到了”，或选择经批准的替代观察 | 观察方式、`accommodations[]` |
| `letter` | 展示署名和主流程摘要 | 摘要完整显示后点击“收好并继续” | 信件 ID；不强制滚动全文 |
| `interaction` | 加载标准化玩法控制器 | 玩法判定成功，或用户确认查看解法 | `outcome`、尝试、提示、辅助方式 |
| `result` | 展示互动终态 | 点击“继续” | `presentationMode`、确认时间 |
| `grant` | 结果 beat 完成后自动激活 | Service 幂等应用 grant；用户点击“收入工具包”后离开该屏 | `grantIds` 和 ledger receipt |
| `map` | 进入转场路线页 | 点击“查看路线” | 路线版本和替代路线 |
| `departure` | 地点最后一个内容完成 | 点击“离开此处” | 章节完成时间；第五章不使用此类型 |
| `journey-depart` | 路线已展示 | 点击“开始前往” | 调用 `beginJourney`，写入 `en_route` |
| `arrival-confirm` | 行程已开始 | 点击“我已到达”或“该点位暂不可达” | 到达模式和替代资料版本 |
| `finale-copy` | 终局结果确认后 | 点击“继续” | `reflectionAcknowledged: true` |
| `finale-message` | 结语确认后 | 保存留言或点击“暂不留言” | 留言和选择状态 |
| `finale-finish` | 留言 beat 完成后 | 点击“完成本次寻迹” | completion receipt |

每种 beat 的后继由配置唯一确定。`grant` 的效果应用和展示确认是两个步骤：Service 先在仍为 `active` 的 beat result 中写入 `effectAppliedAt` 和 receipt，再等待用户确认；确认后才标为 `completed` 并推进。效果 receipt 已写入后即使退出也不能重复发放，恢复时只需继续展示尚未确认的物件卡。

### 7.5 状态写入操作边界

下表中的普通操作各执行一次原子 session mutation 并增加一次 `revision`，操作之间不能合并成页面私有写入。`endSession` 是唯一的多阶段 journal operation，其 lock 与 finalize mutation 分别增加 revision，并在同一 receipt 中记录 revision range：

| 操作 | 原子写入 | 明确不做 |
|---|---|---|
| `activateBeat` | 首次写 `startedAt`；若类型为 `arrival`，同时核对 arrival receipt 并把当前 journey 归回 `idle` | 不完成 beat、不重写到达事实 |
| `saveInteractionSnapshot` | 当前互动快照和 revision | 不推进游标 |
| `completeInteraction` | 标准化互动 result、`completed/assisted`、`completedAt`、下一 result beat 游标；终局板额外写 `final.boardCompleted: true` | 不应用 grant |
| `acknowledgeResult` | result beat 的呈现选择、完成时间、下一 beat 游标 | 不修改 inventory |
| `applyGrant` | effect receipt、grant ledger、inventory/note/status effect | 不完成 grant beat、不推进游标 |
| `acknowledgeGrant` | grant beat 完成时间、下一 beat 游标 | 不再次应用 effect |
| `completePassiveBeat` | content/letter/map/departure 等结果、完成时间、下一游标 | 不越过后继 |
| `setArrivalPending` | journey 写 `arrival_pending`，`arrival-confirm` 成为 current beat | 不创建到达 receipt |
| `confirmArrival` | 完成当前 `arrival-confirm` beat、创建 arrival receipt、写 `arrival_confirmed`、目的地 arrival 游标 | 不重复写到达事实 |
| `endSession` | 完成 finish beat、completion journal/receipt、最终记录和 session 状态 | 不由普通 `completePassiveBeat` 代替 |

快照清理是 `completeInteraction` 成功后的可重试维护步骤，不增加业务 revision；清理失败只占空间，不改变结果。若玩法结果尚未持久化，绝不能清理。

### 7.6 行程与手动到达

地点间行程使用独立对象：

```js
journey: {
  transitionId: 'travel.hhz-hyt',
  fromChapterId: 'huanghuazhen',
  toChapterId: 'haiyantang',
  status: 'en_route',
  startedAt: '...',
  arrivalReceiptId: ''
}
```

状态含义：

| 状态 | 含义 | 恢复位置 |
|---|---|---|
| `idle` | 正在地点内体验，或尚未开始下一段行程 | 当前 beat |
| `en_route` | 已点击前往，尚未发起到达确认 | 地图路线页 |
| `arrival_pending` | 已打开目的地确认卡，但尚未确认 | 目的地确认卡 |
| `arrival_confirmed` | 用户已确认现场到达，或明确选择经审核的不可达替代模式 | 目的地 `arrival` beat |

可玩转场在用户开始实际步行前完成，`en_route` 页面只保留路线、预计方向和“抵达后再操作”提示，不设计要求边走边玩的交互。第一版不读取 GPS；“我已到达”一经确认即保存，刷新或返回不会要求重复确认。

具体转换：`map` beat 展示已审核路线；`travel.*.depart` 使用 `type: 'journey-depart'`，完成时调用 `beginJourney` 写入 `en_route`；用户抵达后点击“抵达后继续”，`setArrivalPending` 写入 `arrival_pending` 并把 `arrival-confirm` 设为当前可激活 beat；`activateBeat` 只记录该确认卡开始时间；最终 `confirmArrival` 明确完成 `arrival-confirm` 并写入 `arrival_confirmed`。任何页面不得跳过这些 Service 转换直接修改 `currentBeatId`。

序章到黄花阵也使用同一模型，`fromChapterId` 为空、`transitionId` 为 `travel.prologue-hhz`，不能绕过第一次“我已到达”。

`confirmArrival` 是到达事实的唯一写入者。它创建不可变 `arrivalReceipt`，写入现场/替代模式、确认时间、路线版本和 fallback asset ID，再把 `currentBeatId` 指向目的地 `arrival` beat。arrival beat 只引用 receipt 并保存用户对到达主视觉的确认，不重复写到达方式或时间。若确认后、目的地页面激活前退出，`getResumeTarget` 根据 `arrival_confirmed` 返回目的地到达页；arrival beat 激活后才把当前 `journey` 归回 `idle`，历史 receipt 继续保存在 `arrivalReceipts` 中。

```js
arrivalReceipt: {
  id: 'arrival.<sessionId>.<chapterId>',
  transitionId: 'travel.hhz-hyt',
  chapterId: 'haiyantang',
  mode: 'onsite', // onsite | remote
  confirmedAt: '...',
  routeAssetRef: { assetId: '...', digest: 'sha256:...' },
  fallbackAssetRef: null,
  accommodations: []
}
```

若点位关闭、施工、拥挤或无可用无障碍路线，到达确认卡提供“该点位暂不可达”。用户进入经审核的替代现场资料，arrival receipt 使用 `mode: 'remote'` 和 `accommodations: ['route-unavailable']`，仍可完成同一观察目标，不记为辅助解题。路线、替代视角和开放信息都属于需现场审核的版本化资产。

已完成章节从地图进入时是只读回看，不改变当前 `journey`、不回退主线游标，也不重复发放物件。未到达章节不能从地图直接开始。

### 7.7 Session 数据模型

以下是 schema v2 的规范最小结构，不是仅供参考的示意：

```js
{
  schemaVersion: 2,
  routeId: 'zodiac-return',
  sessionId: '...',
  revision: 12,
  status: 'in_progress',
  startedAt: '...',
  endedAt: null,
  contentRef: {
    packageId: 'zodiac-return.zh-CN',
    version: '2026-07-narrative-v1',
    digest: 'sha256:...',
    assetManifestDigest: 'sha256:...',
    statusSetRef: {
      id: 'zodiac-status-set.2026-xx',
      digest: 'sha256:...',
      effectiveAsOf: 'YYYY-MM-DD',
      checkedAt: '...',
      maxAgeDays: 30
    }
  },
  preferences: {
    reducedMotion: false
  },
  currentBeatId: 'hyt.water-clock',
  beatProgress: {
    'hhz.maze': {
      status: 'completed',
      completedAt: '...',
      result: {
        outcome: 'solved',
        attempts: 3,
        hintsUsed: ['hint-1'],
        assistance: { method: 'none', solutionShown: false },
        accommodations: ['large-controls'],
        fallbackRef: null
      }
    },
    'hhz.maze.result': {
      status: 'completed',
      completedAt: '...',
      result: { presentationMode: 'full' }
    }
  },
  interactionSnapshots: {},
  chapterProgress: {
    huanghuazhen: { completedAt: '...' }
  },
  journey: {
    transitionId: '',
    fromChapterId: '',
    toChapterId: '',
    status: 'idle',
    startedAt: null,
    arrivalReceiptId: ''
  },
  arrivalReceipts: {},
  inventory: {},
  zodiacStates: {
    granted: false,
    grantedAt: null,
    values: {}
  },
  grantLedger: {
    'artifact.dragon-token': {
      sourceBeatId: 'hhz.token.grant',
      appliedAt: '...',
      receiptId: '...'
    }
  },
  notes: {},
  operationReceipts: {},
  finalizationLock: null,
  final: {
    boardCompleted: false,
    reflectionAcknowledged: false,
    message: '',
    messageChoice: '',
    completionReceiptId: ''
  }
}
```

规范与不变量：

- 除明确标记可空的时间和 receipt 外，上述顶层字段均为必需字段；未知字段按 schema 版本处理，不能静默猜测。
- `status` 枚举为 `in_progress | completed | abandoned | superseded`。只有 `in_progress` 的 `endedAt` 为 `null`；其余状态必须有 `endedAt`。
- `session.status` 是是否完成的唯一权威字段，`final` 不重复保存 `completed` 布尔值；`completed` 必须同时存在 `completionReceiptId`。
- `contentRef` 在 session 创建后不可变。它同时固定内容包、资产 manifest 和尚未向用户发放的状态集；`zodiacStates` 只表示玩家是否已在时间线后获得该快照。
- `revision` 从 0 开始，每次原子 session mutation 严格加 1；普通业务操作只有一次 mutation，`endSession` 的多阶段 mutation 记录在同一 operation receipt 的起止 revision 中。维护性快照清理不改变业务 revision。
- `currentBeatId` 必须属于 `contentRef` 指向的图。`locked` 和 `available` 从图与游标派生，不持久化；只有 `active | completed | assisted` 写入 `beatProgress`。
- completed session 的 `currentBeatId` 保持为 `terminalBeatId`，且该 beat 必须为 `completed`；不使用空字符串表达终点。
- `operationReceipts` 保存已接受操作的 ID、完整 operation fingerprint digest、起止 revision、结果类型和时间，用于确定重放。
- `finalizationLock` 仅由 completion journal 写入；非空时除相同 `endSession` 和 repair 外所有 session mutation 都被拒绝。
- `interactionSnapshots` 只服务当前未完成互动；互动完成后保留标准化 `result`，再按第 7.5 节清理私有快照。
- `arrivalReceipts` 是到达事实的历史记录；当前 `journey` 归回 `idle` 时不删除 receipt。
- 记录页读取 `beatProgress`、`chapterProgress`、`inventory`、`zodiacStates`、`grantLedger` 和去规范化标题，不依赖玩法组件私有结构。

标准化互动 result 必须使用已登记枚举：`outcome`、非负 `attempts`、有序 `hintsUsed[]`、`assistance.method`、`solutionShown`、`accommodations[]`、可空 `fallbackRef`。动画呈现另存于对应 result beat：`presentationMode: 'full' | 'skipped' | 'reduced'`，不能用一个布尔值混淆主动跳过与全局减少动态设置。

`assistance.method` 最小枚举为 `none | show-solution | auto-place | content-fallback`；每个互动可缩小但不能自行增加未登记值。`accommodations[]` 是去重集合，例如 `large-controls`、`alternative-input`；全局 `reducedMotion` 仍保存在 preferences。`fallbackRef` 非空时必须包含 `assetId`、digest、触发原因和等价性审核版本。

章节一至四在各自 `departure` beat 完成时记录 `chapterProgress.completedAt`；第五章在 `hugo.finale.finish` 成功写入 completion receipt 时记录完成时间。

### 7.8 版本与旧记录

`schemaVersion` 表示存储结构，`contentRef.version` 表示不可变文案、素材、beat 和状态集版本，两者不能混用。

旧版采用“去规范化 legacy record + 原始备份”这一种固定策略，不在实现时二选一：

- 当前八站 Demo session 没有 `schemaVersion`，不能直接解释为五章进度。
- 每条旧记录写入路线标题、八个站点标题、状态文字、mark 文案和原时间，不再与当前五章配置动态 join。
- 迁移前把原始 current session、records 和 details 保存到只读 backup key，并记录源 payload digest；损坏数据也保留原文，界面显示“旧记录无法完整读取”，不猜测修复。
- legacy archive ID 使用 `legacy.<原 recordId 或 sessionId>`，v2 session ID 只在用户确认开始新路线后创建，不能在迁移 journal 内提前创建。

迁移 journal key 为 `zodiac.migration.v1-v2`，阶段固定为：

```text
detected
→ raw-backed-up
→ records-denormalized
→ current-archived-as-superseded
→ verified-readable
→ awaiting-user-consent
→ completed
```

每阶段保存 source digest、确定性目标 ID、完成时间和错误。相同 source digest 可重试并继续；digest 变化则停止并重新检测。到 `verified-readable` 前如失败，使用原始备份恢复旧 key；到 `awaiting-user-consent` 后仅展示更新说明，用户点击开始时才创建 v2 session 并写 `completed` receipt。

内容包规则：

- 已完成的八站记录只读展示，不参与新终局道具计算。
- 每个 v2 session 固定一个 `contentRef`。文案、素材、beat 或公开状态变化都发布新包，进行中 session 继续使用原包。
- 至少保留仍有进行中 session 引用的内容包和 asset manifest。若无法保留，必须说明变化并征得用户同意后把旧 session 标为 `superseded`，再新建 session。
- 默认不跨内容包迁移进行中 beat。只有显式声明 `fromDigest`、`toDigest`、beat 映射、grant 映射、回滚和测试 fixture 的迁移才能执行；“找不到 currentBeatId 就回退到第一个未完成 beat”只允许作为该显式迁移内部规则。
- 不做基于数组下标、旧 p1 至 p8 顺序或页面路径的隐式迁移。
- 新记录保存足以独立展示的章节标题、互动标题、状态集 `effectiveAsOf` 和结果摘要，不依赖未来内容配置还原历史记录。

### 7.9 终章与 `endSession`

`hugo.final-board` 的 `completeInteraction` 在同一 session 更新中保存互动结果并把 `final.boardCompleted` 设为 `true`，随后移动到 `hugo.final-board.result`。result 激活不再写完成事实，玩法组件也不能直接调用 `endSession`。

随后由章节控制器依次展示：

```text
hugo.final-board.result    当前获批状态集的完整/追索/未知定格
→ hugo.finale.copy        终章短文；继续后写 reflectionAcknowledged
→ hugo.finale.message     保存留言或明确暂不留言
→ hugo.finale.finish      “完成本次寻迹”
```

只有用户点击“完成本次寻迹”时，Service 才执行 `endSession`；该调用同时完成 `hugo.finale.finish`，普通 `completePassiveBeat` 无权完成它。用户在此之前退出，session 仍为 `in_progress`，根据 `currentBeatId` 恢复到终局结果、终章短文、留言或 `hugo.finale.finish` 按钮，不要求重做终局板。留言为空是合法状态，但必须保存“已选择暂不留言”。

completion 使用确定性 ID：

```text
recordId  = record.v2.<sessionId>
receiptId = completion.v2.<sessionId>
journal   = zodiac.completion.<sessionId>
```

journal 阶段固定为：

```text
prepared
→ session-locked
→ detail-written-pending
→ summary-written-pending
→ session-finalized
→ receipt-written
→ record-published
→ library-merged
→ current-cleared
```

- `prepared` 固定完整 operation fingerprint digest、record ID、receipt ID 和调用时的 `expectedRevision`。
- `session-locked` 原子核对当前仍是 `hugo.finale.finish` 且 revision 未变化，再在 session 写 `finalizationLock` 并增加 revision。锁定后除相同 `endSession`/repair 外拒绝其他写入，避免准备中的留言或状态变化。
- detail 和 summary 先以 `visibility: 'pending'` 写入；即使二者 digest 一致也不能出现在记录列表。
- `session-finalized` 是完成 commit point：在 session 对象中完成 finish beat、写 `endedAt`、`completionReceiptId` 和 `status: completed`，并增加 revision。current session 尚保留供 repair 使用。
- `receipt-written` 把包含 final session digest、record ID 和完成时间的 receipt 写入独立持久 key。
- `record-published` 用 final session digest 更新 detail/summary 并设 `visibility: 'published'`。记录列表只展示 published 且存在匹配 receipt 的记录。
- `library-merged` 把本次已读手记幂等合并到独立 library aggregate；失败可修复，不改写已经 published 的游玩事实。
- `current-cleared` 最后删除 current key；receipt、published record 和 journal 继续保留。此后历史完成权威由 receipt + published record 承担。
- 重复 `endSession(sessionId)` 先查 receipt，相同 operation fingerprint 返回同一结果，不追加记录。
- 启动和打开记录列表时运行 repair：根据 journal 阶段补写 pending record、finalize session、写 receipt、publish 或清理 current key；digest/revision 冲突停止并报告，不覆盖。

本地 storage 没有多键事务，v2 把游标、beat 结果、grant ledger 和 session 状态保存在一个版本化 session 对象中，并使用 revision/operation receipt 恢复中断写入。宿主远程接口必须支持 idempotency key 和版本冲突；因此 v2 Service 方法从一开始按异步接口设计，即使本地实现可以立即 resolve。

最终记录至少包含：

- `schemaVersion` 和完整 `contentRef`。
- 状态集 ID、`effectiveAsOf` 和审核快照。
- 五章完成时间。
- 八互动的 `completed` 或 `assisted` 状态、标准化结果、提示级别、替代操作和减少动态记录。
- 已获得数字物件和兽首公开状态。
- `endSession` 时的手记解锁与阅读快照。
- 最终留言。
- `startedAt`、`endedAt` 和最终完成状态。

手记阅读使用两个明确范围：进行中 session 的 `notes` 保存“本次是否阅读”，由 `markSessionNoteRead` 使用 session revision 更新；完成后资料库使用独立 route/content aggregate：

```js
libraryState: {
  schemaVersion: 1,
  routeId: 'zodiac-return',
  contentDigest: 'sha256:...',
  revision: 0,
  notes: {},
  operationReceipts: {}
}
```

`markLibraryNoteRead` 接收 `{ routeId, contentDigest, expectedLibraryRevision, operationId, noteId }`，不需要已清理的 session key，并遵守同样的完整 fingerprint/receipt 规则。completion journal 的 `library-merged` 阶段把本次已读状态合并进去；用户结束路线后继续阅读只更新 library，不改写记录。记录详情可同时展示“完成时阅读状态”和“当前资料库阅读状态”。

## 8. 文案分层与内容模型

### 8.1 三层文案

| 层级 | 作用 | 建议长度 |
|---|---|---|
| 主流程短句 | 到达、观察、任务、发现和转场 | 单屏一个意思，建议不超过 36 个汉字；真机大字号下不超过三行 |
| 手记摘要 | 林知远的情绪和判断 | 单段约 40 至 80 字 |
| 审核后分章手记 | 可选深读 | 从剧情母本拆分、改写和核验，按章节拆成若干短段 |

### 8.2 每个 Beat 的主流程文字预算

不再用“每章五句话”约束包含多个互动的章节。每个必经 beat 只保留一个主要信息：

1. `arrival`：一句到达钩子。
2. `observe`：一个现场观察目标。
3. `letter`：署名 + 一段一至三行摘要；全文可选。
4. `interaction`：一句当前动作，不在同屏解释完整历史。
5. `result`：一句刚刚发现的内容。
6. `grant`：物件名称和一句用途。
7. `map/departure`：一个下一地点或出发动作。
8. `finale`：每屏一个判断或问题，可连续多屏。

历史背景、人物故事和细节放入可选手记或档案。

### 8.3 叙事声音

| 内容来源 | 视觉语言 | 作用 |
|---|---|---|
| 系统叙事者 | 现代、简洁、直接 | 到达提示、操作、转场和无署名主流程短句 |
| 当前玩家 | 用户自己的选择或留言 | 不替用户写第一人称感受 |
| 陈敬民信件 | 洒金信纸、墨迹、信封 | 发布线索和引导方向 |
| 林知远手记 | 手账纸、批注、日期或编号 | 提供前一位探索者的情绪和思考 |
| 历史档案 | 档案编号、图注、来源标签 | 提供可验证事实 |
| 引文原作者 | 引号、出处和译文信息 | 在信件、手记或档案内部被引用 |
| 剧情化改编 | 明确说明或标签 | 保留文学表达但不冒充史实 |

同一屏只保留一个主要载体。载体内部可以引用他人，但必须同时显示载体作者、引文说话者和出处，不能让用户误以为引文是载体作者本人所说。

人物和载体必须保持以下边界：

- 陈敬民是序章路线说明和五封地点信件的署名者，负责路线指令和信中叙述。
- 林知远是已经走过这条路线的前一位探索者，其内容只能出现在独立手记中。
- 当前玩家不是林知远，不使用“我叫林知远”之类第一人称替玩家作身份决定。
- 从剧情母本改写出的第一人称段落，必须明确归入林知远手记，不能无署名地放到主流程。
- 同一段文字不能同时归属于陈敬民信件、林知远手记和历史档案。
- 陈敬民、林知远及相关文学情节在来源矩阵确认前均按剧情化角色处理。
- “归途未竟，我们仍在路上”等终章主题句归属于系统叙事者；其中“我们”指仍在关注文物去向与历史记忆的当代公众，不伪装成玩家亲口表达。

内容模型区分：

```text
carrierId       当前展示载体，例如陈敬民第二封信
authorId        载体作者，例如陈敬民
quotedSpeakerId 被引用者，例如雨果
claimIds        该原子内容支持或表达的具体 claim
```

一条内容单元只表达一个可独立核验或标注的原子意思。混合事实、引文、文学推断和操作指令的原稿段落必须拆开，不能给整段只挂一个 `classification`。

林知远手记采用固定叙事年份 `2024`，与母本中的“一百六十四年”对应。所有“今天”“一百六十四年后”等相对表述必须放在带日期的林知远手记中，或改写为明确年份；不得让 2026 年及以后游玩的当前玩家继承这些相对时间。

## 21. 史实与剧情化改编

### 21.1 内容分类

内容性质和核验状态是两个维度，不能继续把 `field-check` 与 `fact`、`dramatized` 放在同一个字段里。

内容性质：

```text
fact         可验证事实陈述
quotation    直接或间接引文
dramatized   剧情化角色、事件或文学表达
instruction  路线、现场观察和操作提示
```

核验状态：

```text
draft              草稿，尚未送审
needs-source       缺可靠来源
needs-field-check  需要现场复核
verified           已由指定审核人确认可发布
rejected           已否决，不得使用
```

### 21.4 发布门禁

- 正式内容包只能引用 `verificationStatus: 'verified'` 的内容单元。
- `fact` 必须至少有一个能够直接支持该陈述的来源。
- `quotation` 必须核对原文、译文、说话者和出处，不使用无法定位的名言。
- `dramatized` 必须经过内容审核，并在首次出现时明确标注“剧情化改编”，不能只在之后的可选档案中补充。
- `instruction` 涉及方向、开放区域、可见对象和无障碍条件时，必须完成现场复核。
- 兽首当前所在地、归属和追索状态属于时效性信息，除来源外还要记录 `checkedAt` 和 `maxAgeDays`；默认构建时不得超过 30 天，并在上传体验版前 7 天内人工复核一次。
- 任何 `needs-source`、`needs-field-check` 或 `rejected` 单元被生产配置引用时，内容校验必须失败。
- 带兽首状态 claim 的信件全文、手记、档案和普通图像必须声明 `visibilityAfterGrantId: 'zodiac-status-set.attach'`；图可达性校验发现它们在 `hugo.status-set.grant` 前可见时构建失败。唯一例外是 `hugo.return-timeline` 与其 result 中声明并校验过的 `pinned-status-set.preview`，该能力不能解锁或持久发放状态。
- 非文本互动、答案、复原和示意对象同样必须为 `verificationStatus: 'verified'`，且所有 claim/source 引用存在；待审核对象不能因不属于 `contentUnits` 而绕过门禁。
- 正式素材的 review 和 license 都必须为 `approved`，授权未过期；缺少来源、权限、表现类型、变换记录或 fallback 等价性时阻止生产构建。
- 正式构建前输出“页面/beat → 内容、互动、答案、状态集、素材 → claim/source/license”的可追溯报告，供内容负责人签字确认。

### 22.5 Service 能力边界

页面只通过 Service 推进状态，建议提供：

```text
startSession
getResumeTarget
activateBeat
saveInteractionSnapshot
completeInteraction
acknowledgeResult
applyGrant
acknowledgeGrant
completePassiveBeat
beginJourney
setArrivalPending
confirmArrival
markSessionNoteRead
markLibraryNoteRead
saveFinalMessage
endSession
```

关键要求：

- 所有方法从 v2 起返回 Promise。session 写操作统一接收 `{ sessionId, expectedRevision, operationId, payload }`；`startSession` 和 `markLibraryNoteRead` 使用各自已定义的聚合根/revision envelope。Service 对规范化请求自行计算 fingerprint，不能信任客户端自报指纹。
- `startSession` 尚无 session ID，改用 `{ routeId, clientInstanceId, operationId, payload }`，相同操作重放返回同一新建 session。
- `operationId` 在 route/session 内唯一，receipt 至少保留到 session 和记录保留期结束。
- operation fingerprint 由 Service 规范化计算：`method + routeId + sessionId/clientInstanceId + targetBeatId/resourceId + payload`，不能只比较 payload。
- 相同 operation ID + 相同完整 fingerprint 重放时返回原 receipt，不增加 revision。
- 相同 operation ID 但 method、目标资源或 payload 任一不同，直接返回 `IDEMPOTENCY_MISMATCH`，不写数据。
- 新 operation ID + 过期 revision 返回 `REVISION_CONFLICT` 和最新 revision/session 摘要，不假装成功，也不自动重试写入。
- 已经越过某 beat 的新 operation 若没有可匹配 receipt，返回 `BEAT_ALREADY_ADVANCED`；只有命中原 receipt 才算成功重放。
- 普通成功操作把 revision 增加 1；journal operation 返回起止 revision。响应统一为 `{ outcome: 'applied' | 'replayed', revision, receipt }`，其中 receipt 可含 `fromRevision/toRevision`。
- Service 校验当前 beat 是否允许完成，页面不能通过拼 URL 越过未解锁章节。
- `getResumeTarget` 根据 `currentBeatId` 和 `journey.status` 返回章节、地图或终章，不由各页面自行猜测。
- `endSession` 在已完成时返回同一结果，不重复追加记录。
- 未知 `routeId`、beat ID 或 content version 必须显式报错，不能静默回退到默认路线。
- 本地实现使用 revision、journal 和 receipt 模拟必要原子性；宿主接口必须提供幂等键、条件版本写和 completion receipt，若做不到则需另行设计本地优先同步协议，不能只替换 URL。

### 22.6 配置校验

开发环境和 CI 至少检查：

- beat ID、interaction ID、content unit ID、asset key 和 grant ID 在各自 namespace 内唯一且引用存在。
- `entryBeatId` 和 `terminalBeatId` 存在；每个必经 beat 从入口可达且最终到达终点。
- 除终点外每个必经 beat 都有且只有一个有效 `nextBeatId`，不产生死循环；分组数组顺序必须与 next 链一致。
- 一封序章路线说明与五封地点信归属明确；地点信分别且只归属一个地点，林知远手记不进入必经游标。
- 八互动与第 6.1 节映射一致。
- 所有生产内容都通过第 21.4 节发布门禁。
- 时间线答案、grant、工具包、终局和结语全部引用同一个获批状态集，状态集未过期。
- 每个 beat 类型都有第 7.4 节规定的完成条件和唯一后继。
- 所有关键素材可离线读取或有经过验收的专用 fallback。
- production 配置不注册开发页面、Mock 清理入口、定位调用和未经许可的深链。

### 22.7 旧版冻结与切换条件

在替换 `zodiac-route.js` 前必须先完成：

1. 按第 7.8 节固定策略实现去规范化 legacy record、原始 backup 和不可变 migration receipt。
2. 为旧进行中、已完成、已放弃、损坏和部分写入数据建立迁移 fixtures。
3. 实现带 journal/receipt 的幂等迁移并验证中断后可重试。
4. 新五章 controller、content graph 和 schema v2 自动化通过后，才切换默认入口。
5. 旧模拟器脚本和布局脚本明确标记 legacy；新验收脚本不得继续断言八站、全局 skip 或终局后立即生成记录。

### 22.8 发布构建隔离

- 规划 `npm run build:production` 生成独立 `dist/zodiac-production`，由 production profile 生成 `app.json`、sitemap、分包和内容/素材 manifest；上传命令只接受该目录，默认 fail closed。
- 开发页和 Mock 操作只在明确的 development profile 注册，不能依靠运行时布尔值隐藏。
- `npm run verify:production-artifact` 检查实际生成目录及依赖图，而不只检查源配置；发现 playground、清空进度按钮、Mock 路由/导入、占位答案 `568`、未核实内容、位置 API 或调试深链即失败。
- 生成 sitemap、分包入口和宿主跳转只暴露正式页面；验证 manifest digest 与 session 可固定的 `contentRef` 一致。
- 调试日志不得包含留言、用户标识、位置或完整 session 内容。

## 24. 测试计划

### 24.1 功能测试

- 五章八互动可以完整走通。
- 章节内重复出现的互动、结果和物件 beat 按配置顺序推进。
- 序章到黄花阵及四段章节间转场符合新路线。
- beat、互动快照和章节状态可以保存和恢复。
- `en_route`、`arrival_pending`、`arrival_confirmed` 分别恢复到正确界面。
- 已完成章节可以回看。
- 工具包状态正确。
- 长手记可展开、关闭和稍后阅读。
- 林知远手记保持未读也不会阻塞主线。
- 正常完成与辅助完成都可继续，且记录状态不同。
- 同一 grant 在重复完成回调、返回和重进后只应用一次。
- 旧八站进行中、已完成、已放弃、损坏和部分写入数据不会被错误解释为五章进度，旧记录保持只读。
- 迁移、grant 和终章写入在每个 journal 步骤中断后都可重试。
- 非当前 beat 的深链、重复页面和 stale callback 被 Service 拒绝。
- 进行中 session 固定使用原 `contentRef`，digest 与内容、状态集和资产 manifest 一致，不混用后来发布的内容。
- 终局板完成后退出可恢复到 result、copy、message 或 finish 的实际 beat，不重做终局。
- 留言进入游玩记录。
- `endSession` 只在“完成本次寻迹”后执行，重试不会生成重复记录。
- 自动化至少用真实 WXML tap/input 覆盖正常主路径、一次“查看解法并继续”、首次到达确认和终章留言/finish，不只直接调用页面方法。

### 24.2 叙事测试

每章结束后，首次体验者应能回答：

```text
我在哪里？
为什么要做这个互动？
我刚刚发现了什么？
下一步要去哪里？
```

使用至少 5 名未参与设计的首次体验者。每章结束后至少 4/5 能正确回答上述四问；整体结束后至少 4/5 能分清：

- 哪些话来自陈敬民的序章说明和五封地点信。
- 哪些内容是林知远的前序手记。
- 哪些是历史档案，哪些明确属于剧情化改编。
- 铜板、信件和拓印是小程序中的数字叙事道具。

若任何参与者认为现场真的藏有铜板/信封、尝试接触遗址，或把剧情化人物当成已证实史实，则该轮测试不通过，必须修改首次出现时的标签和文案。

### 24.3 交互测试

- 每屏只有一个主要动作。
- 按钮和拖动对象满足触控尺寸。
- 错误反馈说明原因和下一步。
- 动画期间仍可退出或跳过。
- 返回页面后状态不丢失。
- 不依赖精确小目标点击。
- 辅助完成入口不羞辱用户，也不使用含义不清的“跳过本关”。
- 实际步行阶段不要求用户持续盯屏操作。

### 24.4 视觉测试

- 至少覆盖 320×568、375×812、430×932 三类视口，以及 100% 和 130% 字号。
- 小屏手机不溢出，正文在 130% 字号下仍可滚动和操作。
- 刘海和底部手势区域不遮挡操作。
- 正文对比度至少 4.5:1，大号文字和非文本控件至少 3:1。
- 关键触控区域至少 44×44 CSS px，拖动目标提供等价点击操作。
- 图片裁切不遮挡关键现场对象。
- 五章视觉统一但有各自记忆点。
- 序章首次重点动画前即可开启“减少动态”，设置持久化；开启后不使用路径飞行、持续旋转和强视差，只保留必要终态切换。

### 24.5 性能测试

- 下一章主视觉提前加载。
- 缓存命中时章节外壳 500ms 内可交互，不出现超过 500ms 的空白页。
- 在 1.5Mbps、150ms RTT、1% 丢包的测试网络下，主线依靠已缓存关键素材可继续；高清资源渐进加载。
- 建立并签字确认分包、单章预加载和单素材体积预算，构建超过预算即失败。
- 动画不频繁触发布局计算。
- 在指定低端验收机上，重点动画平均不低于 45fps，点击到视觉反馈 P95 不超过 100ms。
- 启动路线前验证低清关键素材齐备；断网后仍可走完主流程，长手记、高清图和音频可延后。

### 24.6 现场测试

- 至少 5 名首次参与者完成路线，其中至少 1 次实际使用点位不可达或无障碍替代模式。
- 完整路线在计划的 60 至 90 分钟内可完成，单个观察点默认停留不超过 8 分钟。
- 至少 4/5 参与者无需工作人员指点即可从允许通行的视点辨认观察对象。
- 阳光、反光和噪声环境下仍可操作。
- 全流程不出现定位授权提示，也不调用位置 API。
- 人流密集时不要求长时间停留在单一点位。
- 现场网络不稳定时主流程仍可完成。
- 所有观察都能在不触摸、不攀爬和不靠近受限遗址的前提下完成。
- 模拟至少一个点位关闭、施工或路线中断场景，替代资料仍能完成同一学习目标。

### 24.7 配置与内容测试

- 所有 ID 在各自 namespace 内唯一，引用的 beat、互动、内容、素材和 grant 均存在。
- 主线从序章到终章可达，无死路、孤立必经 beat 和无限循环。
- 一封序章路线说明与五封地点信归属明确，五封地点信与五地点一一对应，林知远手记不进入必经游标。
- 生产内容不存在 `draft`、`needs-source`、`needs-field-check` 或 `rejected` 引用。
- 事实、引文和时效性兽首状态具备所需来源与审核信息。
- 时间线答案、grant、记录和终局渲染与同一个未过期获批状态集一致。
- 状态 claim 在 `hugo.status-set.grant` 前只能由 timeline/result 的 preview capability 读取；通过信件全文、手记、档案、工具包和其他图像均不可达，且 preview 不写持久状态。
- 非文本表现对象为 `verified`；每个正式素材 review/license 为 `approved` 且未过期，并具备来源、表现类型、变换记录、digest 和等价 fallback。
- `contentRef` 的 package、状态集和 asset manifest digest 与实际加载文件一致。
- 对生成后的 production artifact 扫描，确认不含开发路由、Mock 清理入口/导入、占位 `568`、位置 API 或调试深链。

### 24.8 并发、Journal 与修复测试

- 相同 operation ID + 相同 payload 重放返回同 receipt，不增加 revision。
- 相同 operation ID + 不同 payload 返回 `IDEMPOTENCY_MISMATCH`。
- 相同 operation ID 和相同 payload 但 method 或 target beat 不同，同样返回 `IDEMPOTENCY_MISMATCH`。
- 两个不同 operation 使用同一 `expectedRevision` 时只有一个成功，另一个返回 `REVISION_CONFLICT`。
- 已越过 beat 的新 operation 返回 `BEAT_ALREADY_ADVANCED`，原 operation 重放仍返回成功 receipt。
- 分别在 `completeInteraction` 持久化前后、snapshot 清理前后、`applyGrant` 前后和 `acknowledgeGrant` 前后中断并恢复。
- 首次和后续行程都覆盖 `en_route`、`arrival_pending`、确认后 destination page 激活前中断，以及 remote arrival receipt。
- 在保存留言后、点击 finish 前退出，恢复到 `hugo.finale.finish`。
- completion journal 的 `prepared`、`session-locked`、`detail-written-pending`、`summary-written-pending`、`session-finalized`、`receipt-written`、`record-published`、`library-merged`、`current-cleared` 每阶段中断后均得到确定修复；在 published + matching receipt 之前记录始终不可见。
- current key 清理后再次 `endSession(sessionId)` 仍从持久 receipt 返回相同 record ID。
- current key 清理后 `markLibraryNoteRead` 使用 library revision 正常写入；记录中的完成时阅读快照保持不变。
- migration journal 每阶段中断、source digest 变化、损坏旧数据和用户尚未同意开始新路线均有 fixture。
- `verify:production-artifact` 检查实际上传目录、生成 manifest 和依赖图，而非仅检查源文件。

## 25. 验收标准

体验版本满足以下条件才算达到完整体验基础：

- 五章和八互动关系清楚。
- 主线由稳定有序 beat 驱动，同章多互动和章节间可玩转场不会丢失状态。
- 玩法不是独立卡片的简单堆叠。
- 一封陈敬民序章说明、五封地点信、数字铜板和独立林知远手记贯穿全程且归属清楚。
- 主流程每个 beat 只表达一个意思，建议不超过 36 个汉字，并通过目标视口和大字号测试。
- 审核后分章手记始终可选，不阻塞操作，不逐字发布未经处理的剧情母本。
- 通关后不会立即自动跳走。
- 辅助完成可继续主线并在记录中如实标记。
- 每章只有一个重点动效。
- 章节之间有明确地图过渡。
- 第一版不请求定位权限、不调用 GPS，并有点位不可达替代模式。
- 故事修改不需要改玩法组件。
- 所有正式内容通过来源和现场核验门禁，史实与剧情化改编有明确说明。
- 数字道具不被描述成现场真实藏物，也不诱导接触遗址。
- 时间线、状态 grant、终局和结语与同一个获批、未过期状态集一致；当前候选仍为七完整、一追索、四空缺。
- 只有用户明确点击“完成本次寻迹”才生成一条最终记录。
- 真机、现场和宿主环境均完成验收。

## 26. 风险与应对

| 风险 | 应对 |
|---|---|
| 剧情仍在调整 | 内容配置与页面代码分离，使用稳定 beat ID |
| 五地点路线尚未现场确认 | 先做路线核实，不锁定距离和到达文案 |
| 史实与文学情节混淆 | 分离内容性质与核验状态，生产构建执行发布门禁 |
| 陈敬民信件与林知远手记混淆 | 分离 author、carrier、quoted speaker、ID 和视觉系统，配置校验一一对应关系 |
| 兽首公开状态变化 | 状态集带有效日期并固定到内容版本，过期即阻止构建，不为保留旧结语覆盖事实 |
| 海晏堂操作过多 | 合并匹配与排序，增加吸附和提示 |
| 八互动仍显得拥挤 | 两个互动转为短转场，最终两个形成连续终章 |
| 八互动被迫一关一印记 | 分离互动结果、数字物件和兽首状态，在时间线统一核验回归状态 |
| 素材来源不清 | 原型可用，正式上线前完成版权核验 |
| 图片和音频导致包体过大 | CDN、按章预加载和格式压缩 |
| 弱网使图片玩法无法完成 | 随包/预缓存关键低清素材，按互动提供专用 fallback 和可记录的辅助完成 |
| 动效过多影响现场操作 | 每章一个重点动效，提供简化模式 |
| 步行时互动带来安全风险 | 可玩转场在出发前完成，`en_route` 只显示静态路线和抵达后再操作提示 |
| 重进导致重复奖励或记录 | beat 完成、grant 和 `endSession` 全部幂等 |
| 旧八站数据被错误恢复 | 使用 `schemaVersion` 显式迁移，旧记录只读展示 |
| 新旧内容在同一 session 混用 | session 固定不可变内容包，旧包保留到 session 结束或经用户同意重启 |
| 点位关闭或路线不可达 | 提供经审核替代路线和现场资料模式，不把身体条件记为解题失败 |
| 宿主技术栈未知 | 保持原生组件和 Service 适配边界 |
| 本地进度无法跨设备 | 先确认一期策略，后续替换 Service 接口 |
