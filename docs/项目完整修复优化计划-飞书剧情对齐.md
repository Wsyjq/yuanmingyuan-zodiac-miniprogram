## 1. 目标与原则

本轮目标不是继续叠加视觉效果，而是先把项目修到以下状态：

1. 玩家可从宿主首页连续完成序章、四站、密码、结局和报告，不出现死路、状态丢失或错误恢复。
2. 页面剧情、谜题答案、卡片数字和结局文案以飞书 revision `2174` 为准。
3. 八张卡片按顺序组成完整日期 `YYYYMMDD`，允许重复数字，并能跨页面、跨重启稳定恢复。
4. 语音回答、四图实拍、海晏堂视频、实体七纹样转盘引导、沿途景点讲解等权威剧情要求得到完整落地，或通过明确审批记录降级。
5. 包体、权限、隐私、宿主 Adapter、版本号和自动化测试达到可发布标准。

执行原则：

- 剧情准确性优先于旧代码兼容；只有存量存档需要迁移兼容。
- 先修 P0 主流程，再补核心玩法，再做视觉精修。
- 每个缺陷先补可复现测试，再修代码。
- 所有异步进度写入必须可串行、可重试、可判定是否真正落库。
- 不以“页面能打开、没有语法错误”作为功能完成标准。

## 5. 必须确认的产品决策

### D1：日期口径

推荐方案：八张卡组成锁定的 `YYYYMMDD`。

- 会话开始时生成 `sessionDate`，格式如 `20260808`。
- 八个卡片位置分别读取索引 0-7。
- 同一会话跨午夜或第二天恢复时仍使用原 `sessionDate`，避免已收集数字与当前时间冲突。
- 如果产品坚持“每次打开都必须是今天”，则跨日时必须提示用户新开考察，不能静默更换答案。
- 飞书当前把前四位写死为 `2/0/2/6`。推荐代码动态取年份，2026 年行为不变，未来年份仍可运行。

### D2：黄花阵“万字纹”如何推出“水”

飞书同时写了“答案万字纹”“寓意福寿绵长”和“谜题答案：水”，逻辑链缺失。

推荐方案：本题答案只认“万字纹”，完成后由路线图或新线索自然引出“海晏堂与大水法”；除非产品补充明确机制，否则不要声称万字纹本身推出“水”。

### D3：水显纸是实体道具还是数字交互（已确认）

产品已确认现场使用实体水显纸。小程序只负责行动提示、答案确认和史料卡，不保留数字 Canvas 或无道具演示模式。

### D4：七纹样与七兽首映射

飞书提供了七种纹样和七尊回归兽首，但没有定义逐项映射、对齐顺序及七段讲解文案。开发前必须由产品/内容方给出一张正式映射表；不得由开发自行编造文化对应关系。

### D5：语音/API 服务归属

推荐由宿主 Adapter 提供统一的 `validateAnswer` 能力，负责语音转写与语义判断；小程序只上传经用户确认的音频或文本。必须确定服务地址、超时、费用、内容安全和降级策略。

### D6：第 N 版是否要求全局唯一

飞书写明“序列递增”。推荐按全局唯一实现，由后端事务或原子计数服务发号；若只需单设备纪念编号，应修改剧情文案，不能继续称全局第 N 版。

### D7：额外结尾视频与考察手册

推荐保留考察手册作为工具能力；结尾视频在素材、文案和播放目的未审批前不作为主流程阻断条件。报告生成后必须可以直接完成体验。

## 6. 目标状态模型

### 6.1 SessionSnapshot v2

建议将当前站级快照升级为可恢复到每道谜题的版本化模型：

```js
{
  schemaVersion: 2,
  sessionId: '...',
  revision: 12,
  sessionDate: '20260808',
  checkpoint: 's3-zodiac',
  stations: { s1: true, s2: true, s3: false, s4: false },
  puzzles: {
    's2-purpose': { completed: true, attempts: 1 },
    's2-name': { completed: true, attempts: 2 },
    's2-blend': { completed: true },
    's2-pattern': { completed: true, attempts: 1 }
  },
  cards: {
    's2-purpose': { position: 0, digit: '2', collectedAt: 0 },
    's2-name': { position: 1, digit: '0', collectedAt: 0 }
  },
  records: [],
  finale: false,
  name: '',
  editionNo: null,
  updatedAt: 0
}
```

### 6.2 八张卡片清单

| position | cardId | 页面 | 数字来源 |
|---:|---|---|---|
| 0 | `s2-purpose` | `s2-quiz` | `sessionDate[0]`，2026 年为 `2` |
| 1 | `s2-name` | `s2-reveal` | `sessionDate[1]`，2026 年为 `0` |
| 2 | `s2-blend` | `s2-blend` | `sessionDate[2]`，2026 年为 `2` |
| 3 | `s2-pattern` | `s2-pattern` | `sessionDate[3]`，2026 年为 `6` |
| 4 | `s3-hour` | `s3-comic` | 月份十位 |
| 5 | `s3-zodiac` | `s3-zodiac` | 月份个位 |
| 6 | `s3-water` | `s3-water` | 日期十位 |
| 7 | `s4-timeline` | `s4-timeline` | 日期个位 |

卡片幂等必须按 `cardId` 判定，不按 digit 判定。密码展示通过 position 排序，未收集位置显示空位，不允许用数组 push 顺序作为唯一依据。

### 6.3 Mutation 规则

1. 所有写入进入单一 Promise 队列，禁止并发提交相同 revision。
2. Adapter 必须显式返回 `{ snapshot, applied, conflict }`，或用可识别的 conflict 错误返回最新快照。
3. 冲突时先合并最新快照，再用同一 operationId 或新的重放 operationId 串行重试。
4. 只有 `applied=true` 后才能发送 `station_completed` / `puzzle_completed` 成功事件。
5. 离线 outbox 至少持久化到本地，应用重启后继续补发；不能只存在模块内存数组。
6. 组合动作优先原子提交，例如水显确认时一次写入 puzzle、card、station 和 checkpoint，避免多命令竞争。

### 6.4 存量存档迁移

这是必须保留兼容的具体场景，因为当前 `plate21_session` 已持久化且已知存在错误数据。

- 新快照写入 `schemaVersion:2`。
- 已完成 `s2` 的旧存档可重建 position 0-3。
- 已完成 `s3` 的旧存档可重建 position 0-6。
- 已完成 `s4` 或 finale 的旧存档可重建 position 0-7。
- 如果 `s4=true` 但 `s3=false`，按已知并发缺陷修复依赖链，将 `s3` 标记完成并记录 migration reason。
- 只完成半站且无法判断具体卡片的旧存档，不猜测；提示从该站首题继续。
- `sessionDate` 优先由旧快照创建时间推导；无法推导时要求用户确认重新开始。
- 迁移前保留一次只读备份，迁移失败时不覆盖旧快照。

## 15. 最终发布验收标准

### 功能

- 宿主首页 → 序章 → 四站 → 8 位密码 → 结局 → 报告全程无死路。
- 每道谜题答错不会锁死，提示层级符合剧情。
- 八张卡按 cardId 和 position 完整展示，重复数字不丢失。
- 任意 checkpoint 退出和冷启动后准确恢复。
- 重新考察创建新 session，不继承旧进度。

### 剧情

- 文案与飞书 revision `2174` 对齐。
- 语音/文字、四图实拍、视频、实体转盘、实体水显纸、三景讲解均完成或有批准降级。
- 解题前不出现答案史料卡或排序答案。
- 结局和报告表达一致，不混入废弃五站剧情。

### 数据

- mutation 冲突、离线、重复点击和重试均不丢数据、不重复应用。
- 成功埋点只在真实成功后发送。
- 全局版号同 session 幂等、跨用户递增。
- v1 存档迁移可验证、可回退。

### 质量

- 单元、组件、E2E、视觉和包体检查全部通过并返回正确退出码。
- 微信开发者工具控制台无 error/exception。
- iOS/Android 真机关键路径通过。
- 报告图片中主图、边框、题跋、姓名、日期和版号均清晰且层级正确。

### 发布

- 包体满足微信当期限制并保留至少 20% 余量。
- 正式 appid、请求域名、CDN、隐私声明和权限说明齐全。
- 有版本号、变更日志、监控指标和可用回滚包。
